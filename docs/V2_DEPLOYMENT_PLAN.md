# План переходу V1 → V2

**Статус:** підготовчий план. Production deployment заборонений до окремого письмового дозволу капітана №5 і призначення фінального release SHA.

**База для плану:** `feature/integration` на `8779302bdfc7385741d7b4778d09198e1e769da0` (PR #15). Це контрольна точка підготовки документа, **не** затверджений release SHA.

**Ціль:** замінити V1 на V2 після перевірки сумісності й міграції. V1 зберігати як rollback-артефакт до успішного завершення погодженого періоду стабілізації V2.

## Підтверджений стан і межі знань

- Backend FastAPI використовує SQLite; схема у коді має `SCHEMA_VERSION = 2`. Backend викликає `migrate(engine)` під час імпорту/запуску застосунку. Отже, перший старт release-кандидата може змінити базу автоматично.
- На репозиторії є `frontend/pnpm-lock.yaml`; точні версії Node.js і pnpm для сервера та production-конфігурації потрібно зафіксувати разом із release SHA.
- Analytics UI/API підключені у V2. Аналітична методика `team-results-demo-0.1` є авторською демонстраційною пропозицією; `approval_status=proposed`, `synthetic_only=true`. Для маршрутів потрібен `INTEGRITY_ANALYTICS_DEMO=1`, але він не перевіряє походження записів.
- Поточна роль передається заголовком `X-Role`. Документація визначає це як демо-механізм, не справжню автентифікацію.
- У переглянутому коді не знайдено реалізації автентифікації через cookies, CSRF-захисту чи 2FA. Їхню готовність слід позначити **NOT IMPLEMENTED / NOT VERIFIED** до окремої реалізації й QA. Не можна подавати цей прототип як захищену систему для реальних користувачів або даних.
- WinSW і Caddy production-конфігурації не зберігаються в репозиторії. Поточні шляхи, аргументи служб, змінні середовища, ACL і Caddyfile мають бути зняті з сервера власником у режимі читання та збережені у захищеному runbook без секретів.
- За звітом №4: серверний Git object store старого каталогу пошкоджений/пов’язаний з OneDrive; робочу БД не можна змінювати до погодження міграції. Останній відомий звіт про backup: integrity/FK checks та локальне відновлення пройшли; незалежне відновлення в іншому Windows-профілі **NOT VERIFIED**; шифрування локальної позасерверної копії не перевірено. Переперевірити ці відомості перед deployment.
- Deployed SHA, поточний стан служб і production Caddy rules зараз вважати **NOT VERIFIED**, доки власник не надасть новий серверний аудит.

## Блокери до production deployment

1. №5 письмово затверджує точний release SHA, вікно робіт, прийнятний режим демонстрації та go/no-go відповідальних.
2. №2 погоджує схему міграції і перелік даних, які мають зберегтися. Міграцію не запускають на робочій БД до перевірки цієї специфікації на копії.
3. Зовнішня резервна копія має бути захищена шифруванням і ACL. Відновлення має перевірятися незалежно від поточного Windows-профілю. Якщо інший профіль/пристрій недоступний — так і записати, не заявляти PASS.
4. Потрібні свіжий backup перед роботами, перевірені integrity/FK checks, збіг контрольних сум копії, і перевірене відновлення. Зберігання backup/ключа має бути незалежним від сервера та профілю оператора; ключ не потрапляє до Git, логів чи цього документа.
5. Потрібні production-налаштування WinSW, Caddy, firewall/Tailscale, шляхи до release та змінні середовища. Вони мають зберігатися у захищеній конфігурації, без секретів у репозиторії.
6. Потрібне явне рішення щодо автентифікації, cookies, CSRF і 2FA. Поточний `X-Role` сам по собі не захищає API. Не відкривати публічний запис і не використовувати реальні дані.
7. Потрібно вирішити, що означає «повноцінна V2» для Survey: Caddy зараз обмежує записувальні HTTP-методи для публічної демонстрації, тоді як подання анкет потребує POST. До окремого безпечного рішення зберігати read-only правила; інтерактивне подання тестувати локально на синтетичній БД.
8. Потрібні успішні чиста збірка, міграційна перевірка та smoke tests на ізольованій копії з точним release SHA.

## Підготовчі кроки без зміни сервера

1. Зняти інвентар V1 у режимі читання: фактичний Git SHA (якщо доступний), конфігурацію служб і Caddy, версії Python/Node/pnpm, шляхи коду/БД, firewall/Tailscale, startup type і scheduled tasks. Не запускати `git pull` у старому OneDrive-каталозі.
2. Зберегти копії V1-коду, WinSW/Caddy-конфігурації та параметрів служб у захищеному архіві поза OneDrive; секрети винести у захищене сховище, зафіксувати лише назви/посилання на секрети.
3. Перевірити зовнішній backup: шифрування, ACL, контрольна сума, можливість розблокування відновлювальним ключем іншим профілем/пристроєм. Після розпакування перевірити SQLite `integrity_check` та `foreign_key_check` на тимчасовій копії.
4. Створити release-кандидат у новому каталозі поза OneDrive лише після отримання точного SHA. Не переключати вказівники служб.

## Перевірка release-кандидата на ізольованій БД

Виконувати на окремій машині/каталозі та копії БД, не на production. Точні команди залежать від погодженого SHA та серверного середовища.

1. Отримати чистий clone/fetch на release SHA; перевірити `git rev-parse HEAD` і чистий `git status`.
2. Перевірити lockfile та toolchain; frontend встановлювати відтворювано через `pnpm install --frozen-lockfile`, потім виконати frontend tests і production build.
3. Встановити backend залежності з погодженого lock/requirements набору у чисте середовище; запустити повний backend suite.
4. Зробити копію погодженої БД v1. Зафіксувати SHA-256 до запуску кандидата, версію `PRAGMA user_version`, кількість анкет/відповідей та інші погоджені контрольні підсумки.
5. Вказати кандидату шлях лише на копію через `INTEGRITY_DB`. Запуск коду може автоматично виконати міграцію; перевірити резервну копію, версію схеми, збереження очікуваних даних, `integrity_check=ok` і порожній `foreign_key_check`.
6. Перевірити `/api/health`, основні Survey read/write сценарії локально, права ролей і журнал аудиту на синтетичній БД.
7. Analytics маршрути перевіряти тільки на синтетичній БД з явним `INTEGRITY_ANALYTICS_DEMO=1`: methodology, index, recommendations, comparisons. Успіх означає коректні відповіді та збереження `proposed`, `synthetic_only=true` і `limited_comparability` там, де застосовно. Не використовувати це env значення на production БД.
8. Перевірити Caddy `/api` proxy і доступ до frontend. На доступі для журі залишити заблокованими POST/PUT/PATCH/DELETE, доки №5 окремо не затвердить модель безпечного Survey write flow. Не робити запити, здатні змінити спільну БД.

## План перемикання після окремого дозволу

Це майбутня процедура, не дозвіл на виконання.

1. Зафіксувати погоджений SHA, час робіт і відповідального за go/no-go. Переконатися, що оператор має консольний/адміністративний шлях відновлення.
2. Перевірити стан V1, поточні WinSW service definitions, Caddyfile, startup settings, порти, журнали, місця коду й БД. Зберегти старі конфігурації та контрольні суми.
3. Повідомити користувачів і зупинити запис до БД у погоджене вікно; перевірити, що writers зупинились. Якщо запис неможливо заморозити — зупинити план і погодити консистентний backup спосіб.
4. Створити SQLite backup через коректний SQLite backup-механізм; скопіювати його на затверджене зашифроване сховище. Перевірити контрольні суми, integrity/FK checks і доступність ключа відновлення. Вихідний V1-файл не перезаписувати.
5. Переконатися, що release-каталог побудований точно з погодженого SHA, конфігурація вказує на production DB лише після backup і містить потрібні змінні. Analytics opt-in лишити `0`/відсутнім для робочої БД, якщо окремо не затверджено синтетичну ізольовану конфігурацію.
6. Зупинити Backend/Caddy за погодженою процедурою WinSW. Змінити лише погоджені service paths/config. Запуск нового backend може змінити схему БД: робити це тільки після backup і погодження №2.
7. Запустити backend, переглянути міграційний лог, health endpoint і міграційні перевірки; потім перевірити Caddy, frontend та дозволені API. Переконатися, що write methods лишилися заблоковані для публічного демонстраційного доступу.
8. Виконати погоджений smoke checklist із синтетичними сценаріями. Порівняти DB контрольні підсумки, журнали й доступність; не вважати успішний `/api/health` достатнім доказом правильної міграції.
9. №4 надає факти, №5 приймає go/no-go. Без явного go від №5 — відкат.

## Умови зупинки та rollback

Негайно зупинити перемикання, якщо SHA не відповідає погодженому; backup не читається/не перевіряється; міграція чи перевірки integrity/FK не проходять; рядки/контрольні підсумки не збігаються; немає необхідних секретів/конфігурації; Caddy проксуює не туди або дозволяє непогоджений запис; health/API/Survey smoke tests не проходять.

Rollback виконувати лише за погодженим runbook: зупинити нові сервіси та будь-яких writers; повернути WinSW і Caddy конфігурації V1; повернути V1 код із незмінного архіву/каталогу; якщо міграція змінила схему — відновити перевірену backup БД V1 за умови, що в V2 ще не було прийнятих записів. Якщо V2 уже прийняла записи, не відновлювати стару копію поверх них без рішення №2/№5 — спершу зберегти стан і погодити перенесення нових даних. Запустити V1 і перевірити health та погоджений smoke test. Старий V1 не видаляти до підтвердження стабільності V2 і окремого дозволу на прибирання.

Повернення V1 коду/конфігурації/БД ще не вважається перевіреним лише тому, що локально протестовано відновлення копії. Якщо ізольована репетиція не охопила кожен крок — позначити відповідний крок **NOT VERIFIED**.

## Відкриті рішення для №5

- Призначити release SHA після завершення Survey і фінального frontend Analytics QA.
- Погодити, чи V2 на сервері лишається приватною read-only демонстрацією, поки реальна автентифікація/CSRF/2FA відсутні.
- Визначити безпечний сценарій Survey подання: Caddy read-only блокує POST, але Survey потребує запису. Не послаблювати обмеження без рішення.
- Погодити з №2 міграційну специфікацію, збереження та обробку нових записів при rollback.
- Погодити захищене зовнішнє сховище backup і незалежне відновлення; шифрування та restore в іншому профілі зараз не підтверджені.
- Погодити точні WinSW/Caddy параметри, назви сервісів, вікно, відповідальних і smoke критерії.
- Погодити строки зберігання V1 та умови архівації/видалення після стабілізації V2.

## Уточнення архітектури V2 — аудит №4, 17.11.2026

Детальна матриця сумісності: [V2_ANALYTICS_COMPATIBILITY.md](V2_ANALYTICS_COMPATIBILITY.md). В актуальному коді @ `8779302b` чотири Analytics GET-маршрути вже підключено до Dashboard. Поточні обчислення і read-only API можна зберегти для синтетичної демонстрації; контракт №2/№3 визначить необхідні зміни схеми й агрегатів. `X-Role` не придатний як V2 авторизація. Login/logout, HttpOnly cookies, CSRF, 2FA та рольова модель user/admin ще не реалізовані на цьому SHA.

Перед тестовим розгортанням №3/№5 мають затвердити контракт: `POST /api/auth/login`, `POST /api/auth/logout`, перевірку сесії, cookie `HttpOnly`/`Secure`/`SameSite`, CSRF для state-changing методів, 2FA для визначених ролей, статуси 401/403 і серверну матрицю дозволів. Назви маршрутів тут **пропозиція**, не наявний API. №2/№3 узгоджують відокремлення identity від анонімних анкет, версії анкет і популяцій для Comparative Analytics. До цього не створювати production identity-схему і не заявляти повну порівнянність циклів.

Майбутній Caddy має пропускати лише конкретні погоджені write-маршрути: login/logout, Survey POST та інші окремо затверджені операції; backend перевіряє сесію, роль і CSRF. Caddy маршрутизує й обмежує доступ, але не замінює перевірок backend. Поточне загальне блокування POST/PUT/PATCH/DELETE зберігати до прийнятого контракту, реалізації та ізольованого security QA. Перевірити, що запити на непогоджені write routes повертають відмову й що Survey POST не пов'язує особу з відповіддю.

V1 код і конфігурації зберігати як незмінну точку відкату; перед перемиканням потрібен свіжий перевірений backup V1 БД. Локальна репетиція rollback — PASS за попереднім звітом; серверний WinSW/Caddy/DB rollback — NOT VERIFIED. Зашифрована зовнішня `.gpg` копія й локальне відновлення — PASS за попереднім звітом; незалежне Windows-profile restore — NOT VERIFIED. Кандидат `12aad16` пройшов локальний QA, але фінальний production SHA ще не призначено. На призначеному SHA повторити ізольовані збірку, міграцію копії, Analytics/Survey smoke, auth/CSRF/2FA і rollback перед окремим дозволом №5.
