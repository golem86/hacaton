## 1. Два контури даних

| | Персональний контур | Анонімний контур (Survey) |
| --- | --- | --- |
| Призначення | особисте самооцінювання й навчання | оцінювання системи доброчесності закладу |
| Ідентифікація | `user_id` з серверної сесії | **жодної**: без акаунта, сесії, імені |
| Сховище | `v2_auth.db`: `v2_user_attempts` | `INTEGRITY_DB` (V1): `response_sets`, `answers` |
| Доступ | лише власник (перевірка на сервері) | лише агрегати після приховування малих груп |
| Вплив на Integrity Index | **немає** | **єдине джерело** |
| Захист від повторних відповідей | одна чернетка на тестування; завершену не змінити | одноразовий код доступу |

**Єдине офіційне джерело анонімних відповідей — Survey API + `INTEGRITY_DB`.** Маршрути `/v2/anonymous/*` і БД `v2-anonymous-local.db` прототипу вилучаються (дані в ній синтетичні й локальні, перенесення не потрібне).

### 1.1 Правила Survey

| Ситуація | Результат |
| --- | --- |
| Відкритий цикл + валідний невикористаний код цього циклу + коректна анкета | `201 {"status": "accepted"}` — без номера анкети |
| Закритий цикл | `409` |
| Повторне використання коду | `403` (те саме повідомлення, що для вигаданого чи чужого коду) |
| Некоректна анкета (шкала, дублі, неповна, категорія, підрозділ) | `422`, код **не витрачається** |
| Одночасні запити з одним кодом | рівно один `201` (атомарне погашення) |

### 1.2 Наскрізна анонімність

Жоден з елементів — код, акаунт, сесія, метадані — не дозволяє пов'язати відповідь з особою:

| Рівень | Правило |
| --- | --- |
| Frontend | анонімний режим надсилає запити з `credentials: 'omit'`: cookie сесії не передається, навіть якщо користувач увійшов |
| Маршрут подання | не читає cookie сесії і не приймає `X-Role`; доступ лише за одноразовим кодом |
| Код доступу | погашається атомарно разом зі збереженням анкети; у БД немає зв'язку код ↔ анкета (`access_tokens` посилається лише на цикл) |
| БД | в анкеті лише цикл, категорія, підрозділ з довідника; без `user_id`, email, IP, User-Agent, часу подання |
| Відповідь сервера | без номера анкети |
| Журнал дій | подання анкет не журналюються |
| Журнали веб-сервера й reverse proxy | без IP і часу для `POST …/submissions` |
| Агрегати | первинне й вторинне приховування малих груп; без розбивки для відкритого циклу |

### 1.3 Видача кодів

Коди видає адміністратор: `POST /api/assessments/{id}/tokens?count=N` (сесія `admin`, CSRF). Кожна видача потрапляє в Audit Trail **лише як кількість**. Сервер не знає і не зберігає, кому видано який код: роздача анонімна (організаційне правило), статус окремого коду не віддається жодним маршрутом.

## 2. Ролі й автентифікація

| Хто | Як визначається | Що може |
| --- | --- | --- |
| `admin` | серверна сесія з 2FA | керування оцінюванням, коди, агрегати, Analytics, Audit Trail, звіти |
| `user` | серверна сесія з 2FA | лише власні персональні тестування |
| Анонімний респондент | **без акаунта**, лише одноразовий код | анкета Survey |
| `auditor` | **відкрите питання №5** | за замовчуванням роль не існує; Audit Trail доступний лише `admin` |

### 2.1 Три класи маршрутів

| Клас | Маршрути | Що дає доступ | Що ігнорується |
| --- | --- | --- | --- |
| **Публічні GET** | `GET /api/health`, `/api/assessments`, `/api/assessments/{id}`, `/api/assessments/{id}/questionnaires`, `/api/units`, `/v2/auth/csrf` | нічого не потрібно; лише читання нечутливих даних | cookie сесії, `X-Role` |
| **Анонімний Survey POST** | `POST /api/assessments/{id}/submissions` | **лише** одноразовий код у тілі запиту | cookie сесії, `X-Role` |
| **Захищені** | усі інші маршрути розділу 3 | **лише** перевірена серверна сесія (verified principal) з потрібною роллю | `X-Role` |

`X-Role` не впливає на **жоден** клас: не відкриває доступ, не змінює роль, не змінює відповідь. Публічні маршрути автентифікаційних дій (`/v2/auth/register`, `/login`, `/password-reset/*`) не дають доступу до даних і захищені CSRF (розділ 3.0).

Правила:

- роль визначає **лише перевірена серверна сесія** (verified principal); `X-Role` у релізі не обробляється взагалі — підроблений заголовок не дає доступу;
- legacy `/api/*` використовують той самий principal, що й `/v2/*`; ролі V1 `manager`, `anticorruption`, `respondent`, `expert`, `data_officer` у V2 не використовуються;
- `admin` створюється лише локальною CLI-командою; публічна реєстрація завжди дає `user` (PASS);
- сесія: cookie з префіксом `__Host-`, HttpOnly, `SameSite=Lax`, `Secure` у релізі, 12 год, **новий токен (і новий CSRF-токен) після 2FA**.

## 3. API Contract для frontend

Позначення: **Сесія** — cookie сесії після 2FA; **Pending** — сесія до 2FA; **CSRF** — перевірка за контрактом розділу 3.0. Помилки: `401` — немає сесії або 2FA; `403` — немає прав, CSRF не пройдено або недійсний код; `404` — не знайдено або не належить користувачу; `409` — конфлікт стану; `422` — помилка валідації; `429` — ліміт спроб.

### 3.0 CSRF-контракт

Прототип використовує простий double-submit (cookie `v2_csrf` = заголовок `X-CSRF-Token`). Його недостатньо: токен не прив'язаний до сесії, а cookie можна підмінити (cookie injection з піддомену або через HTTP). Для V2 діє така схема:

| Захист | Правило |
| --- | --- |
| Прив'язка до сесії | для автентифікованих операцій CSRF-токен **прив'язаний до сесії**: сервер видає його разом із сесією і зберігає лише хеш поруч із сесією (або обчислює як HMAC від ідентифікатора сесії серверним секретом). Токен іншої сесії або старої сесії → 403. Після ротації сесії (вхід, 2FA, вихід) видається новий токен |
| Дії до входу | для `/v2/auth/register`, `/login`, `/password-reset/*` — **підписаний** токен (HMAC серверним секретом), прив'язаний до pre-auth cookie; непідписаний або чужий токен → 403 |
| Захист від підміни cookie | cookie сесії й CSRF мають префікс `__Host-` (`Secure`, `Path=/`, без `Domain`), тож піддомен чи HTTP-сторінка не можуть їх встановити або перезаписати |
| Перевірка походження | для **кожного** запиту зміни стану з cookie-авторизацією сервер перевіряє `Origin` (а за його відсутності — `Referer`) за allowlist погодженого frontend-домену. Чуже походження → 403; у `release` запит без обох заголовків → 403 |
| Додатковий рівень | `SameSite=Lax` для cookie сесії лишається, але **не вважається** самостійним захистом |
| Сфера | усі POST/PUT/PATCH/DELETE з cookie-авторизацією (`/v2/*` і адміністративні `/api/*`). Анонімний Survey POST не використовує cookie (розділ 2.1), тож замість CSRF захищений одноразовим кодом |

Приймальні тести (S4): без токена; токен іншої сесії; токен до ротації сесії; непідписаний pre-auth токен; чужий `Origin`; відсутні `Origin` і `Referer` у `release`; спроба встановити cookie без префікса `__Host-` — усі → 403.
