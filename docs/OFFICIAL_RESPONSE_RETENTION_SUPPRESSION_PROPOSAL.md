# Пропозиція: retention та suppression офіційних анонімних відповідей

**Статус: PROPOSAL ДЛЯ №5 / НЕ production policy.** Цей документ описує цільові правила для окремих `official_response_sets` і `official_answers`. Чинна schema 3 та production API не змінюються. Ізольований test-only прототип не встановлює строки зберігання чи production suppression.

## Фактичні дані прототипу

Тестова БД `backend/prototypes/official_expert.py` зберігає для набору відповідей випадковий внутрішній ID, cycle ID, template ID/version і категорію. Відповіді зберігають question ID та option ID. Немає respondent/user ID, access token, token digest, IP, user agent або часу створення відповіді. Токен у окремій таблиці кодів представлений HMAC digest, циклом, категорією, строком дії й прапорцем використання; посилання на набір відповідей відсутнє. Клієнт не отримує внутрішній ID.

Прототип поки зберігає використаний digest коду до ручного видалення тестової БД. Для циклу/відповідей у ньому немає delete API, retention job, suppression query чи управлінського dashboard. Це відома незавершена частина, а не прихована властивість прототипу.

## Пропонована класифікація зберігання

| Дані | Пропозиція | Причина / обмеження |
| --- | --- | --- |
| `official_answers` | Зберігати лише question ID і option ID; видаляти разом із response set. | Відповідь є описовою; не переводити її у бал без окремої методики. |
| `official_response_sets` | Випадковий внутрішній ключ, cycle, затверджена template/version і лише погоджений широкий category. Не повертати ключ клієнту. | Немає прямого зв’язку з людиною чи кодом. Категорія може сама ідентифікувати малу групу, тому її використання залежить від suppression. |
| Код доступу | HMAC digest, cycle/category, expiry та one-time state в окремій таблиці; без response ID. Видаляти після закриття циклу та затвердженого операційного grace interval. | Digest не є відповіддю, але під час перевірки лишається контрольним секретом. Строк grace має визначити №5. |
| Підсумкові агрегати | Лише агрегати, що пройшли suppression; без експорту рядків відповідей. | Зниження ризику ідентифікації та виведення відповідей за відніманням. |
| Access/security audit | Дія, сервісний результат і мінімальний cycle reference; ніколи не тіло запиту, option ID, код, cookie чи respondent ID. | Діагностичний журнал не має ставати другим сховищем відповідей. Конкретний allowlist і строк зберігання погодити. |

Не створювати вільне текстове поле, точний timestamp відповіді, email, user ID, IP, device ID або зв’язок token ↔ answer. Не додавати прихованих полів до аналітики. Якщо законний/операційний аудит вимагатиме додаткових даних, спершу оцінити ризик повторної ідентифікації й отримати окреме погодження.

## Строки й видалення

Рекомендований життєвий цикл:

1. У відкритому циклі приймати відповіді; сирі рядки недоступні адміністративному Dashboard.
2. Після закриття циклу заборонити нові записи, зафіксувати версію шаблону й виконати контроль цілісності. Не показувати live розбивку.
3. Показати лише агрегати, які відповідають затвердженому порогу та правилам проти differencing. Зберігати сирі рядки лише на період, який №5 затвердить для перевірки якості/оскарження/перерахунку.
4. Після затвердженого строку видалити response sets та answers однією транзакцією, видалити кодові digest-и циклу і похідні кеші/експорти. Не залишати резервну копію без окремої retention дати.
5. Документувати лише факт виконання purge, cycle reference і підсумок операції; не логувати видалені опції чи рядки відповідей.

Точну кількість днів неможливо безпечно вивести з поточного контракту. №5 має визначити початок відліку (закриття чи затвердження звіту), строк на оскарження, максимальний строк raw retention, строки логів/backup та винятки. Якщо законодавство або правила організації вимагають довшого зберігання, потрібна окрема правова/методична підстава й оцінка анонімності.

SQLite delete сам по собі не гарантує фізичного стирання старих сторінок, WAL, snapshot чи файлових backup. Production план має включати FK cascade/транзакційне видалення, перевірку WAL checkpoint, контроль lifecycle backup, обмежений доступ до файлу БД і, якщо політика вимагає, `secure_delete`/перебудову БД. Не запускати vacuum або purge на production до затвердження runbook і відновлювального тесту.

## Suppression та повторна ідентифікація

- Застосовувати чинний затверджений поріг `k` до кожної категорії й кожного зрізу; не вигадувати нове число. Поки №5 не визначив відповідність і поріг для офіційних анкет, не показувати їхні розбивки.
- Приховувати малу групу та взаємно відновлювані групи: якщо прихований сегмент можна отримати як загальний підсумок мінус видимі сегменти, приховати також достатню частину суміжних підсумків (complementary suppression).
- Не давати комбінувати форму, цикл, category, підрозділ і часовий інтервал так, щоб повторні запити звужували групу. Не надавати детальні зрізи, близькі за складом, і не дозволяти порівняння довільних підмножин.
- Не публікувати поточну кількість відповідей/відсоток завершення для малих груп; не показувати точні timestamp або порядок надходження.
- У звітах маркувати пригнічені дані як «недостатньо відповідей», не як 0. Не повертати точну приховану кількість у metadata, error, CSV/XLSX чи API side channel.
- Експертні оцінки тримати в окремому сховищі й не поєднувати з анонімними відповідями. Експертна роль не дає доступу до raw anonymous rows.

Застосування suppression до `mgmt`, `npp`, `cadets`, `staff` і робочої групи залежить від погодженого mapping; самі назви категорій не доводять достатній розмір або анонімність. Анкета 2 не маршрутизується автоматично до рішення №5.

## Журнали, IP і rate limiting

Анонімний endpoint має бути поза автентифікованою cookie-сесією та відхиляти cookie/Authorization. Reverse proxy, CDN, ASGI access logger, error tracker і tracing мають виключити request body, query з кодами, cookie, CSRF та Authorization. Код передавати лише в body; ніколи в URL. Для відповіді клієнту повертати generic помилки без input values.

Поточний test app не має proxy, production access logs чи rate limiter, отже ці ризики не перевірені в deployed середовищі. Перед інтеграцією потрібні конфігураційні тести ingress/proxy/logger. Для rate limiting спершу віддавати перевагу одноразовому коду, лімітам циклу та загальному ліміту запитів без зберігання IP. Якщо захист від distributed abuse потребуватиме IP-based обмежень, зберігати лише короткоживучий HMAC/агрегат із ротацією ключа й TTL, без сирого IP, і затвердити це окремо. Такий псевдонім усе ще є потенційно персональним даним, а не анонімним фактом.

## Рішення №5

1. Поріг `k`, набір дозволених зрізів і complementary suppression для малих/перетинних груп.
2. Чи дозволено категорію/підрозділ у raw response set і які категорії мають бути приховані повністю.
3. Точка початку та максимальна тривалість raw retention; строк видалення code digest-ів, логів, export/cache та backup.
4. Правила доступу для перегляду агрегатів і чи допускається якийсь тимчасовий контроль сирих рядків.
5. Rate-limit модель, дозволені ingress security metadata та строки їх зберігання.
6. Точний purge runbook для SQLite/WAL/backup, доказ завершення видалення й порядок відновлення.
7. Повідомлення респондентам про анонімність, межі конфіденційності та обробку малих груп.

До цих рішень прототип не слід підключати до production. Цей документ не надає дозволу на production DDL/API, міграцію, збір IP чи зміну retention чинної системи.
