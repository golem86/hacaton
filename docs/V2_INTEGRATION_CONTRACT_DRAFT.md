## 2. Контракт агрегатів для Analytics

Базовим джерелом Index лишається агрегований `GET /api/assessments/{id}/results` для **закритого анонімного циклу**. Персональні тести виключені до окремого погодження методики №2/№3/№4/№5. №2 фіксує версію анкети, ідентифікатори питань/компонентів, категорії, шкали, популяцію циклу, правила агрегації й мінімальний розмір групи `k`; №3 підтверджує frontend-поля й стани. Поточні поля та маршрути бажано зберегти сумісними; зміни оформити версією контракту, не тихою заміною значень.

Для всіх агрегованих зрізів: первинне й вторинне приховування малих груп; приховані чисельності, score і похідні значення → `null`; Index, Recommendations і Comparisons не відновлюють приховані дані. Порівняння між циклами лишається `limited_comparability`, поки не доведено сумісність версій анкет, методики й популяцій. `approval_status=proposed`, `synthetic_only=true` для поточної демометодики.

## 3. Безпековий контракт до інтеграції

- Усі `/api/*` і V2 endpoints мають отримувати роль/особу з перевіреної сесії. Клієнтський `X-Role` і прямий заголовок не надають прав. Неавторизований запит → 401, недостатні права/чужий персональний запис → 403 або погоджений 404 без витоку існування.
- `dev-mail`/OTP тестовий канал відсутній у release-конфігурації та недоступний через Caddy. Визначити production доставку OTP, TTL, rate limit і спосіб зберігання секретів.
- Для cookie-auth state-changing `/v2/user/*`, Survey POST, login/logout та інших дозволених записів №2 задає CSRF-механізм, cookie `HttpOnly`, `Secure`, `SameSite`, expiry/rotation та 2FA-політику. №3 реалізує frontend за цим контрактом. Backend перевіряє сесію, CSRF і власника; Caddy пропускає лише погоджені маршрути.
- Негативні тести після виправлень: підроблений `X-Role`, пряма адреса `/api/*`, чужий `user_id`, відсутній/хибний CSRF, обхід 2FA, доступ до `dev-mail`, непогоджені write-методи, повторне подання анкети, виведення малих груп через кілька запитів.
