## Конкретні несумісності й рішення

1. `backend/app/roles.py` довіряє довільному `X-Role`; `frontend/src/api/client.ts` завжди його надсилає. Це не автентифікація. Для V2 потрібен перевірений principal із серверної сесії та матриця дозволів, узгоджена №3/№5. Самого перейменування `respondent` на `user` недостатньо.
2. У коді немає login/logout, HttpOnly session cookies, CSRF і 2FA. Їхні маршрути, cookie атрибути, строк сесії, CSRF-механізм і 2FA-політика потребують окремого контракту; Analytics слід адаптувати після нього.
3. `INTEGRITY_ANALYTICS_DEMO=1` відкриває обчислювальні маршрути для синтетичної БД, але не перевіряє її походження. Методика доступна без прапорця. Не вмикати прапорець на спільній робочій БД.
4. Порівняння циклів не має доказу порівнянності історичних анкет і популяцій. Статус `limited_comparability` зберігати до контракту версіонування №2/№3.
5. Схема відділяє одноразові коди від анонімних відповідей. Нова identity-схема не повинна додати прямий або часовий зв'язок, що деанонімізує анкету. Перевірити міжзапитове виведення малих груп при нових V2 фільтрах.
6. Caddy read-only блокує Survey POST і майбутні login/logout/write операції. Правила маршрутизації й CSRF слід погодити до будь-якого послаблення; поточний сервер не змінювати.

## Межа змін

Зберегти поточні формулу, розрахунок, пропозиції та read-only маршрути, якщо контракт №2/№3 підтвердить структуру агрегатів. Адаптувати role dependency, frontend API client, історичне порівняння й нові write workflows після погодження API/схеми. Міграції тестувати тільки на ізольованій копії або синтетичній БД.
