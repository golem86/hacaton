# Оновлення бази даних

> **Чинні версії:** integrity schema **7**, auth schema **2**. Цей документ детально описує перші міграції V1 (0 → 1 → 2); подальші версії додавали коди-хеші (5), Додаток В (6) і `user_units` (7) за тим самим механізмом. **У release автоміграцію вимкнено:** сервер лише перевіряє схему, а оновлення робить `Update-V2InPlace.ps1` з резервною копією й автоматичним відкатом (`installer/windows-v2/docs/UPGRADE_IN_PLACE.md`). Резервні копії робочого сервера — [BACKUP_RESTORE.md](BACKUP_RESTORE.md). Приклади з `X-Role` нижче діють лише в режимі development.

У режимі development бекенд сам доводить SQLite-базу до поточної схеми під час запуску (`backend/app/migrations.py`). Анкети й відповіді при цьому не стираються.

## Версії схеми

Версія зберігається в самій базі: `PRAGMA user_version`.

| Версія | Що змінилося |
| --- | --- |
| 0 | Попередня версія (PR #4): підрозділ — довільний текст, відповіді без обмеження унікальності |
| 1 | Довідник `units`; `response_sets.unit` посилається на `units.name`; у `answers` одна відповідь на пару «анкета + питання»; SQLite перевіряє зовнішні ключі |
| 2 | Таблиця журналу дій `audit_events`. Лише додається нова таблиця, наявні таблиці й дані не змінюються, тому оновлення 1 → 2 не перебудовує таблиць і не створює резервної копії |

## Що відбувається під час оновлення 0 → 1

1. **Резервна копія.** Поруч з базою створюється `integrity.backup-<дата>-<час>.db` (через вбудований механізм SQLite backup). Файли `*.db` не потрапляють у git.
2. **Перевірка дублікатів.** Якщо в старій базі є дві відповіді на одне питання в одній анкеті, оновлення зупиняється з поясненням. Дублікати не видаляються автоматично: рішення ухвалює людина.
3. **Перенесення в одній транзакції:**
   - усі наявні назви підрозділів переносяться в довідник `units`;
   - таблиці `response_sets` і `answers` перебудовуються з новими обмеженнями, усі рядки копіюються з тими самими номерами.
4. **Перевірки перед збереженням:** кількість анкет і відповідей не змінилася, `PRAGMA foreign_key_check` порожній, `PRAGMA integrity_check` = `ok`.
5. Якщо будь-яка перевірка не пройшла, **усі зміни відкочуються**, база лишається такою, як була, а в помилці вказано шлях до резервної копії.

Повторний запуск нічого не змінює і нової копії не створює.

## Процедура оновлення

1. Зупиніть сервер (`Ctrl+C`).
2. Отримайте нову версію коду (`git pull`).
3. Оновіть залежності, якщо вони змінилися:

   ```powershell
   cd backend
   .\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-dev.txt
   ```

4. Запустіть сервер як зазвичай:

   ```powershell
   .\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
   ```

   Якщо базу оновлено, у консолі з'явиться `База оновлена до нової схеми. Резервна копія: …`.
5. Перевірте: `GET /api/units` (заголовок `X-Role: respondent`) повертає непорожній список.

Якщо з'явилася помилка `MigrationError`, сервер не запускається, а база не змінена. Виправте причину, вказану в повідомленні (наприклад, дублікати), і запустіть сервер знову. Повернутися до стану до оновлення можна, скопіювавши файл резервної копії на місце `integrity.db`.

## Демонстраційні дані

`python -m app.seed --reset` **стирає всі дані**. Використовуйте його лише для окремої синтетичної бази, наприклад:

```powershell
$env:INTEGRITY_DB = "demo.db"; .\.venv\Scripts\python.exe -m app.seed --reset
```

Без `--reset` seed відмовляється змінювати базу, у якій уже є дані.

## Перевірка

Тести міграції (`backend/tests/test_migration.py`) створюють базу у схемі попередньої версії і перевіряють:

- збереження кожної анкети й відповіді без змін;
- перенесення підрозділів у довідник;
- створення резервної копії з оригінальними даними;
- роботу нових обмежень після оновлення;
- повторний запуск без змін;
- зупинку й відкат за наявності дублікатів;
- приймання API анкети зі старим підрозділом.
