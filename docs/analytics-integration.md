Реалізовано read-only маршрути index, methodologies, comparisons, recommendations. Вони працюють через той самий assessment_results(), що обслуговує чинний GET /results, із SQLite та закритими циклами. Немає mock-відповідей, зовнішнього AI, прихованих ваг чи повторного перетворення 0–100. Роутер окремо перевіряє ті самі дозволені ролі, бо прямий виклик Python-функції не запускає FastAPI dependencies автоматично.

## Запуск

Уже встановлених залежностей backend достатньо. Python 3.12 перевірено.

Linux/macOS, з backend:

```bash
INTEGRITY_DB=/tmp/integrity-analytics-synthetic.db python -m app.seed
INTEGRITY_DB=/tmp/integrity-analytics-synthetic.db INTEGRITY_ANALYTICS_DEMO=1 python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Windows PowerShell, з backend і активованою .venv:

```powershell
$env:INTEGRITY_DB = Join-Path (Get-Location) 'integrity-analytics-synthetic.db'
python -m app.seed
$env:INTEGRITY_ANALYTICS_DEMO = "1"
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`INTEGRITY_DB` має вказувати на окремий файл лише для синтетичних даних; не задавайте типовий шлях застосунку або спільну БД. Команди seed запускайте лише для нового порожнього файлу. Не використовуйте `--reset` для наявної бази. `INTEGRITY_ANALYTICS_DEMO=1` тільки відкриває маршрути й **не перевіряє походження записів**. `synthetic_only=true` — декларація методики, не автоматична перевірка БД. Seed-цикл 1 закритий, цикл 3 відкритий: для нього обчислення дадуть 409 до явного закриття адміністратором.

```bash
curl -H 'X-Role: manager' 'http://127.0.0.1:8000/api/assessments/1/index?methodology=team-results-demo-0.1'
```

Очікується HTTP 200, status=ok, 7 компонентів, index від 0 до 100, approval_status=proposed. Точне число залежить від синтетичної БД. Для семи однакових балів 50 результат точно 50. Немає opt-in — 503, неправильні ваги — 409, немає methodology — 422. Докладний контракт — docs/API_CONTRACT.md.

## Що треба узгодити учасникам №2, №3 й інтегратору

1. Або прийняти цю інтеграційну демоверсію із сімома seed-компонентами та обґрунтувати їхні ваги, або змінити каталог на конкретні питання додатків Б/В і створити нову версію. Попередні три критерії з demo-0.2 не відображаються автоматично в C1–C7.
2. Додати незмінну версію каталогу/методики та популяцію до кожного циклу для надійного порівняння в часі. Хеш поточної відповіді не замінює збереження її знімка.
3. Якщо потрібна експертна оцінка — окреме джерело, рубрика та докази. Не використовувати категорію mgmt як замінник.
4. Додати одиниці, metric_id, походження й докази для об’єктивних фактів.
5. Підключити frontend до задокументованих маршрутів, показувати null/приховування й proposed-статус. Цей PR не змінює UI іншого учасника.
6. Окремо підключити persistence Tracker, історію, людське прийняття та перевірку наступним оцінюванням. Готова доменна функція не перевіряє реальну сесію користувача.

Tracker відхиляє той самий assessment ID незалежно від того, чи він переданий як число, чи як десятковий рядок. Перевірку хронології слід визначити окремо через дати циклів у БД; числове порівняння ID для цього непридатне. До цього доменна функція лише перевіряє, що ID різні.

Цей документ і код є конкретною пропозицією для рев’ю, а не свідченням того, що інші учасники вже погодили методику.
