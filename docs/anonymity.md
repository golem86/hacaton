# Захист анонімності респондентів

Документ описує, як Integrity Management Dashboard захищає анонімність учасників опитування, які правила приховування малих груп реалізовано, де межі демонстраційної рольової моделі та які ризики залишаються відкритими.

**Статус:** зафіксований код `6629c74` (20.11.2026), він же працює на робочому сервері. Усі дані синтетичні. Методика з 7 компонентів демонстраційна і не має статусу офіційно затвердженої. Поріг групи `k = 5` є демо-налаштуванням, а не гарантією анонімності для реальних даних.

Код: `backend/app/models.py`, `backend/app/anonymity.py`, `backend/app/routes/assessments.py`, `backend/app/routes/results.py`. Тести: `backend/tests/test_database.py`, `test_api.py`, `test_results.py`, `test_migration.py`.

## 1. Принципи

1. **Оцінюється система, а не люди.** Результати показують стан компонентів доброчесності закладу. API не повертає жодних даних про окремого респондента чи окремого керівника.
2. **Анонімність закладено в структуру даних**, а не лише в інтерфейс. Чого немає в базі, того не можна розкрити ні запитом, ні помилкою в коді.
3. **Сервер — межа захисту.** Усі перевірки (ролі, приховування, статус циклу) виконує бекенд. Інтерфейс лише відображає те, що дозволив сервер.

## 2. Що зберігається і чого навмисно немає

| Таблиця | Що зберігається | Чого немає |
| --- | --- | --- |
| `response_sets` (анкета) | цикл, категорія респондента, підрозділ із довідника | імені, ID користувача, email, IP, часу подання |
| `answers` (відповіді) | анкета, питання, значення | будь-якого зв'язку з людиною чи кодом доступу |
| `access_tokens` (коди доступу) | SHA-256 коду (відкритий код показується лише один раз під час видачі), цикл, ознака «використано» | відкритого коду; посилання на анкету; часу використання |
| `units` (довідник підрозділів) | назви підрозділів | — |
| `user_units` (підрозділ користувача V2, схема 7) | id користувача з V2_AUTH_DB, підрозділ із довідника, час призначення | email, імені, зв'язку з анкетами й кодами доступу (не видно, чи подавав користувач анкету) |

Ключові рішення:

- **Код доступу не пов'язаний з анкетою.** Таблиця кодів посилається лише на цикл. Відомо, *що* код використано, але не *яку* анкету ним подано. Це перевіряє тест `test_token_not_linked_to_responses` і `test_no_link_between_tokens_and_responses_in_schema`.
- **Немає часу подання.** Без позначок часу анкету не можна зіставити з тим, коли конкретна людина була біля комп'ютера.
- **Підрозділ лише з довідника.** Довільний текст (наприклад «Іваненко, кімн. 214») відхиляє і API (422), і сама база (зовнішній ключ на `units.name`). Так у базу не потрапляють персональні дані і не можна створити «підрозділ з однієї людини».
- **Цілісність гарантує база.** SQLite перевіряє зовнішні ключі, а на пару «анкета + питання» допускається лише одна відповідь.

## 3. Подання анкети

`POST /api/assessments/{id}/submissions`

1. Акаунт не потрібен: доступ дає лише одноразовий код у тілі запиту (не в URL). Перевіряються існування і статус циклу, категорія, підрозділ, повнота анкети й межі шкали.
2. Код доступу **погашається атомарно** одним оператором `UPDATE … WHERE token_hash = … AND used = false` разом зі збереженням анкети в одній транзакції: або обидва, або нічого. Подати двічі тим самим кодом неможливо, навіть за одночасних запитів.
3. Якщо анкета не пройшла перевірку (422), код **не витрачається**.
4. Відповідь сервера — лише `201 {"status": "accepted"}`. **Номер анкети не повертається**, щоб його не можна було зіставити з кодом.
5. Для недійсного, чужого і вже використаного коду повертається **одне й те саме** повідомлення (403). Так перебором не можна дізнатися, які коди існують.

## 4. Приховування малих груп

Функції `hidden_flags()` і `suppress_small_groups()` у `backend/app/anonymity.py` використовуються **кожною** адресою, що віддає дані по групах.

### 4.1 Первинне приховування

Група з кількістю анкет менше `k` (`min_group_size` циклу, у демо 5) приховується. В API (`/results`, `/participation`) прихована група **не повертається зовсім**, ні з назвою, ні без неї. Видимі групи мають `hidden: false` для сумісності, а прапорець `suppressed: true` повідомляє, що щось приховано (`visible_groups` в `anonymity.py`). Модуль зрілості за Додатком В показує приховану категорію як `level: null, hidden: true` ([maturity-annex-v.md](maturity-annex-v.md)).

### 4.2 Вторинне приховування

Приховати лише малу групу недостатньо: якщо відомий загальний підсумок, то *прихована група = підсумок − сума видимих*.

Правило: **у межах кожного відомого підсумку сума прихованих груп дорівнює 0 або не менша за k.** Якщо це не так, додатково приховується найменша видима група, доки умова не виконається. Тоді з різниці можна дізнатися лише суму кількох груп (≥ k), але не розмір чи бал однієї.

Приклад із демо-даних (цикл 1, k = 5):

| Категорія | Анкет | Показується | Причина |
| --- | --- | --- | --- |
| `cadets` | 210 | 210 | — |
| `npp` | 48 | 48 | — |
| `mgmt` | 6 | приховано | вторинне: інакше `staff = 268 − 210 − 48 − 6 = 4` |
| `staff` | 4 | приховано | первинне: 4 < 5 |

Правило перевірено на 2000 випадкових наборів груп (`test_hidden_flags_property_on_many_random_cases`).

### 4.3 Розбивка «категорія × підрозділ»

`GET /participation?by_unit=true`:

- для кожної категорії діє те саме правило відносно **підсумку цієї категорії**;
- категорія, прихована в загальній розбивці, приховується **в усіх своїх підрозділах**, щоб її не можна було «зібрати» з клітинок.

Перевіряється тестом `test_hidden_unit_cell_cannot_be_recovered_from_category_total`.

### 4.4 Відкритий цикл

Поки оцінювання відкрите:

- `GET /participation` показує лише загальну кількість анкет, **без розбивки**; кількості округлюються вниз до кратного 5 і показуються, лише якщо вони не менші за k (`counts_exact: false`), тож одна нова анкета зазвичай не змінює відповіді;
- `GET /results` повертає 409.

Інакше, порівнявши дві відповіді сервера до і після подання конкретної анкети, можна було б дізнатися її категорію або відповіді. Результати стають доступними лише після закриття циклу адміністратором (`POST /close`).

### 4.5 Агреговані результати

`GET /results` віддає лише середні бали по компонентах загалом і по категоріях. Окремі анкети та відповіді не віддаються жодною адресою. Приховування категорій однакове для всіх компонентів і збігається з `participation`. Загальний бал показується, лише якщо загальна кількість анкет ≥ k. Модуль аналітики (Integrity Index, порівняння, рекомендації) отримує дані **лише через `/results`**, тобто вже після приховування.

### 4.6 Результати підрозділу для користувача

Звичайний користувач бачить середні бали C1–C7 **лише свого** підрозділу за закритий цикл
(`GET /v2/user/unit-results`, лише роль `user`). Підрозділ (таблиця `user_units`) призначає тільки власник сервера
командою `python -m app.v2_unit_cli set-unit --email <email> --unit "<назва з довідника>" [--confirm]`
(`clear-unit` — зняти, `list-units` — довідник; без `--confirm` — лише план); кожна зміна — подія журналу
`user.unit_change` без email, id і назви підрозділу. Клієнт не передає ні підрозділ, ні категорію, ні інших фільтрів.

Результат показується, лише якщо: (1) у підрозділі ≥ k анкет **і** (2) у **всьому** циклі кожна непорожня
клітинка «категорія × підрозділ» має ≥ k анкет. Правило (2) глобальне свідомо: бали підрозділів (їх бачать
різні користувачі), бали категорій (`/results`) і загальний бал — суми по клітинках однієї таблиці, тож
будь-яке віднімання між ними (змова користувачів із різних підрозділів, переведення користувача, користувач
разом із керівництвом) дає лише суму цілих клітинок, кожна з яких ≥ k людей. Незалежна перевірка відновила
бали одного керівника за слабшого правила («підрозділ ≥ k і решта циклу ≥ k»); цей сценарій тепер —
регресійний тест. Кількість анкет округлюється вниз до кратного 5, порожній і малий підрозділ дають однакову
відповідь, чернетка циклу не відрізняється від неіснуючого. Наслідок: якщо в циклі є хоч одна мала клітинка
(наприклад, 1–4 керівники в різних підрозділах), результати підрозділів за цей цикл не показуються взагалі.
Залишковий ризик: k−1 учасників одного підрозділу у змові, віднявши власні відповіді, отримують відповіді
останнього — як і для будь-якого агрегата з порогом k.
У прихованій відповіді (`privacy_status = suppressed`) `responses` і всі бали — null; без призначеного
підрозділу — `no_unit` з `unit = null`. Відома прогалина: `Cache-Control: no-store` для цього маршруту не встановлюється
(як і для інших `/v2/user/*`).

## 5. Рольова модель

Роль визначає лише сервер за перевіреною сесією V2: вхід з паролем і кодом 2FA поштою, CSRF для запитів, що змінюють дані (`backend/app/roles.py`).

| Хто | Може | Як отримує доступ |
| --- | --- | --- |
| Респондент | бачити анкету й подати її | без акаунта, за одноразовим кодом |
| `user` | особистий кабінет: тестування, статистика, «Результати підрозділу» | самореєстрація |
| `data_officer` | видавати коди, бачити участь (результатів **не** бачить), вносити чек-лист і об'єктивні показники | призначає лише власник сервера з консолі |
| `admin` | цикли, результати, аналітика, трекер, звіти, журнал дій, а також права `data_officer` | призначає лише власник сервера з консолі |

Помилки: `401` — немає перевіреної сесії, `403` — немає прав або не пройдено CSRF.

У вебі ролі `admin` і `data_officer` не призначаються, тож самопідвищення прав неможливе. Свідомо прийнятий ризик: адміністратор сам видає коди й бачить результати, тому атака n−1 технічно доступна будь-якому адміністратору. Запобіжники — контрольоване коло адміністраторів, журнали й поріг k ([abuse-analysis.md](abuse-analysis.md), п. 10).

Демонстраційний заголовок `X-Role` з першого прототипу **не є автентифікацією й у release не діє**: він обробляється лише в режимі development з прапорцем `INTEGRITY_DEMO_XROLE=1` для регресійних тестів, а release-сервер із цим прапорцем не стартує.

## 6. Журнал дій

Журнал фіксує адміністративні операції (видача кодів, керування циклами, рішення трекера, зміни ролей тощо): хто (роль і id користувача), що, коли і над яким циклом.

Журнал **не містить**:

- кодів доступу;
- відповідей анкет і будь-яких їхніх ознак;
- категорії чи підрозділу респондента;
- записів про подання анкет: подання не журналюється, бо запис «анкету подано о 10:42» разом із розкладом людей міг би розкрити автора.

Зміна підрозділу користувача V2 серверною командою журналюється як `user.unit_change` (`actor_role = server`) без email,
id користувача й назви підрозділу.

## 7. Відомі ризики й обмеження

| Ризик | Чому існує | Як зменшити |
| --- | --- | --- |
| Адміністратор сам видає коди й бачить результати (атака n−1) | рішення власника сервера | контрольоване коло адміністраторів, журнал `tokens.issue`, поріг k ([abuse-analysis.md](abuse-analysis.md), п. 10) |
| Адміністратор знає, кому видав який код | коди генеруються в системі | роздавати коди випадково (запечатані конверти, лотерея), не записувати, хто отримав який код |
| Видно, *хто взяв участь*, якщо коди видавалися персонально | у кодах зберігається ознака «використано» | анонімна роздача кодів; не показувати статус окремого коду (жодна адреса API його не віддає) |
| Порядок записів у SQLite відповідає порядку подання | автоматична нумерація рядків | не давати доступ до сирого файлу бази; для реального розгортання перемішувати або видаляти службові ID |
| Журнали веб-сервера (IP і час запиту) | веб-сервери за замовчуванням пишуть access log | на робочому сервері вимкнено: uvicorn з `--no-access-log`, у Caddy access log не вмикається, журнал помилок без IP і URI. При іншому розгортанні треба повторити |
| Порівняння між циклами з різними учасниками | зміна складу груп між циклами | порівнювати лише цикли з погодженою популяцією; поріг k для кожного зрізу |
| Малі підрозділи | поріг k = 5 є демо-налаштуванням | визначити k і правила публікації для реальних даних до впровадження |
| Резервні копії містять ті самі дані | щоденні копії й копії перед оновленням | доступ лише Administrators і SYSTEM, зайві копії видаляються ([BACKUP_RESTORE.md](BACKUP_RESTORE.md)) |
| Змова k−1 учасників одного підрозділу | властивість будь-якого агрегату з порогом k | достатньо великий k для реальних підрозділів (розділ 4.6) |
| Експертні оцінки без підтвердних документів | експертне оцінювання за Додатком В реалізовано, але сховища доказів (Evidence Repository) немає | окреме сховище підтвердних матеріалів з правилами доступу |

Ці ризики не стосуються демонстрації на синтетичних даних, але **мають бути закриті до роботи з реальними респондентами**.

## 8. Як перевірити

```powershell
cd backend
.\.venv\Scripts\python.exe -m pytest
```

Тести перевіряють:

- відсутність полів про особу в анкеті та зв'язку код ↔ анкета;
- одноразовість коду, однакову відповідь на чужий і вигаданий код, незгоряння коду при помилці;
- первинне і вторинне приховування, розбивку по підрозділах, відсутність розбивки й результатів для відкритого циклу;
- відхилення підрозділу не з довідника і дубльованих відповідей на рівні бази;
- результати підрозділу для користувача: лише роль `user`, приховування за малими клітинками всього циклу, однакова відповідь для порожнього й малого підрозділу, призначення лише командою сервера (`backend/tests/test_v2_unit_results.py`);
- права ролей на всіх адресах;
- відсутність кодів і відповідей у журналі дій.
