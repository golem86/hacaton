# Концепція інтеграції з іншими цифровими рішеннями у сфері доброчесності

Пункт здачі 12. Документ описує, як Integrity Management Dashboard працює як модуль закритої відомчої мережі і як він обмінюється даними з іншими системами. Також тут подано поетапну дорожню карту.

Документ доповнює, а не повторює:

- [integration-map.md](integration-map.md) (пункт 9): компоненти, потоки даних, наявні маршрути, типові точки інтеграції, перехід на іншу СУБД;
- [abuse-analysis.md](abuse-analysis.md) (пункт 10): загрози, запобіжники, обов'язкові умови перед роботою з реальними даними.

**Стан коду:** зафіксований код `6629c74` (20.11.2026), він же працює на робочому сервері. Концепція — пропозиція команди. Конкретні системи визначає замовник. Назви нижче — узагальнені класи систем.

## 1. Розгортання в закритому відомчому контурі без хмари

| Частина | Як працює | Зовнішні залежності під час роботи |
| --- | --- | --- |
| Frontend | Зібраний React/Vite-застосунок роздає Caddy (`frontend/Caddyfile`); `/api`, `/v2`, `/docs` проксуються на backend з того самого origin | Немає (без CDN) |
| Backend | FastAPI, Python 3.13 (`backend/Dockerfile`), uvicorn з `--no-access-log` | Лише SMTP для кодів 2FA (необов'язково в development) |
| Дані | Дві SQLite-бази в окремому volume: `integrity.db` (анонімний контур: цикли, відповіді, факти, журнал дій) і `v2_auth.db` (облікові записи, сесії, персональні тестування) | Немає |
| Документація API | Swagger UI з локальних файлів `backend/app/static/swagger-ui/`, лише для адміністратора з 2FA | Немає |
| Звіти PDF | Кириличний шрифт вбудовано локально (`backend/app/static/report-font/`) | Немає |
| Рекомендації | Детерміновані правила, без ШІ | Немає |

`compose.yaml` описує два сервіси в окремій мережі Docker `demo_net` (bridge). Назовні відкрито лише порт frontend, і лише на `127.0.0.1`; backend власного порту на хості не має. Backend працює з `no-new-privileges` і `cap_drop: ALL`, має healthcheck `/api/health`. Секрет `V2_SECRET_KEY` зберігається лише в локальному `.env`, якого немає ні в Git, ні в build context. Покроковий запуск — у [DOCKER_DEMO.md](DOCKER_DEMO.md). Цей пакет призначений для локальної демонстрації, а не для production.

Щоб модуль працював у мережі без доступу до інтернету, потрібно:

1. **Образи й залежності з внутрішнього реєстру.** Базові образи `python:3.13-slim-bookworm`, `node:22-bookworm-slim`, `caddy:2.10-alpine` і зафіксовані залежності (`backend/requirements.txt`, `frontend/pnpm-lock.yaml`) беруться з внутрішнього дзеркала. Інший варіант — завчасно зібрані образи, перенесені погодженим способом.
2. **Внутрішній поштовий сервер для 2FA.** Підключення задають `V2_SMTP_HOST` і `V2_SMTP_PORT` (типово 587). STARTTLS обов'язковий, сертифікат і ім'я хоста перевіряються (`v2_auth.py`, `smtp_tls_context`). Сертифікат внутрішнього центру сертифікації має бути в довірених на сервері.
3. **Release-конфігурація** за [V2_INTEGRATION_CONTRACT.md](V2_INTEGRATION_CONTRACT.md), розділи 4–5:
   - `APP_ENV=release`;
   - HTTPS на reverse proxy з внутрішнім сертифікатом і `Secure` cookie;
   - `TRUSTED_PROXIES` лише для власного proxy;
   - міграції явною командою, а не автоматично;
   - у журналах proxy немає IP для `POST …/submissions`.
4. **Резервні копії** обох баз з тими самими обмеженнями доступу ([abuse-analysis.md](abuse-analysis.md), розділ 8).

Без Docker backend і frontend запускаються за [LOCAL_DEV.md](LOCAL_DEV.md). Інсталятор для Windows (`installer/windows-v2/`) уже в `main`: ним розгорнуто робочий сервер, де backend, Caddy і локальна модель працюють як окремі служби. Оновлення на місці — з резервною копією й автоматичним відкатом.

## 2. API як точка інтеграції

- Канонічні маршрути даних — `/api/*`. Автентифікація, персональний модуль і звіти — `/v2/*`. Схема OpenAPI (`/openapi.json`, `/docs`) доступна лише адміністратору після 2FA ([API_CONTRACT.md](API_CONTRACT.md), розділ «Документація API»).
- Маршрути поділено на три класи: публічні GET, анонімне подання анкети за одноразовим кодом і захищені маршрути ([V2_INTEGRATION_CONTRACT.md](V2_INTEGRATION_CONTRACT.md), розділ 2.1).

| Потреба зовнішньої системи | Маршрут | Доступ |
| --- | --- | --- |
| Перелік циклів, анкета, довідник підрозділів | `GET /api/assessments`, `/api/assessments/{id}/questionnaires`, `/api/units` | Публічний GET, без чутливих даних |
| Агреговані результати закритого циклу | `GET /api/assessments/{id}/results` | Сесія `admin` |
| Індекс, рекомендації, порівняння | `GET /api/assessments/{id}/index`, `/recommendations`, `/api/analytics/comparisons` з обов'язковим `methodology=` | Сесія `admin`; демо-прапорець |
| Звіт і файли | `GET /v2/admin/reports/{id}`, `/v2/admin/reports/{id}/export?format=pdf\|xlsx` | Сесія `admin` |
| Журнал адміністративних дій | `GET /api/audit-events` | Сесія `admin` |

**Головна прогалина.** Доступу «система — система» немає. У release захищені маршрути приймають лише cookie-сесію людини після 2FA, а зміни стану додатково потребують CSRF. Сервісних облікових записів і токенів для інтеграції немає. Пропозиція (етап 2) така:

- окрема роль лише для читання агрегатів закритих циклів;
- взаємна TLS-автентифікація всередині контуру або короткострокові токени від відомчої системи ідентифікації;
- запис кожного звернення в журнал дій.

Стабільність контракту: формати `/results`, `/index`, `/recommendations` і `/comparisons` зафіксовано (MIG-3 у V2-контракті). Версія методики явно передається в запиті й повертається у відповіді. `input_sha256` і `config_sha256` дозволяють системі-отримувачу перевірити, що вона має той самий вхід і ту саму конфігурацію розрахунку ([methodology.md](methodology.md), розділ 4).

## 3. Формати експорту

| Формат | Що містить | Для кого |
| --- | --- | --- |
| JSON (API) | Агрегати, індекс, пропозиції, порівняння з версією методики та хешами | Аналітичні системи керівництва, інші модулі |
| PDF | Звіт `integrity-report-{id}.pdf`: таблиці «Підсумок», «Бали компонентів», «Участь за категоріями», «Бали за категоріями»; приховане позначено «Приховано», відсутнє — «Немає даних»; вбудований шрифт, номери сторінок | Система електронного документообігу, керівництво |
| XLSX | Ті самі таблиці на аркуші «Звіт»; рядки записуються як текст (`strings_to_formulas=False`, `strings_to_urls=False`), тож назва циклу не стане формулою | Аналітики |

Обидва файли будуються з тих самих агрегатів і правил приховування, що й `/results` (`backend/app/services/reporting.py`, `report_tables`). Сирі відповіді, коди доступу та Integrity Index не експортуються ([V2_INTEGRATION_CONTRACT.md](V2_INTEGRATION_CONTRACT.md), розділ 3.3).

Пропозиції на майбутнє:

- додати в експорт індекс із версією методики й хешами, коли методику затвердять;
- файл обміну JSON для передавання без мережевого з'єднання;
- підписання звіту засобами електронного підпису, прийнятими в системі електронного документообігу замовника.

## 4. Ідентифікація і єдиний вхід (SSO) — майбутня робота

**Зараз:**

- локальні облікові записи в `v2_auth.db`: пароль і одноразовий код поштою (2FA);
- cookie сесії `HttpOnly`, `SameSite=Lax`, строк 12 год; у режимі Secure (release, HTTPS) — з префіксом `__Host-`; CSRF прив'язано до сесії;
- ролі `admin`, `data_officer` і `user`. Першого адміністратора створює локальна CLI-команда `app.v2_bootstrap_admin`, а ролі `admin` і `data_officer` призначає лише власник сервера командою `app.v2_role_cli` (у вебі — 403);
- роль визначається в одному місці: `backend/app/roles.py`, `resolve_principal`.

**Пропозиція:**

1. Підключити відомчу систему ідентифікації через стандартний протокол (OpenID Connect або SAML 2.0). Вона підтверджує особу й членство в групах, а модуль зіставляє групи з ролями `admin`, `user` і в майбутньому `auditor` (відкрите питання V2-контракту). Другий фактор забезпечує система ідентифікації.
2. Замінити лише джерело principal у `resolve_principal` і `require_v2_role`. Правила доступу на маршрутах не змінюються.
3. Після переходу вимкнути локальні облікові записи в release або залишити один аварійний обліковий запис адміністратора. Це вирішує замовник.
4. **Анонімна анкета лишається поза SSO.** Маршрут подання не читає cookie, frontend надсилає анкету з `credentials: 'omit'`, доступ дає лише одноразовий код. Якщо вимагати вхід для анкети, журнали системи ідентифікації пов'язали б особу з часом подання.

Відкриті питання для замовника:

- яка система ідентифікації;
- зіставлення груп і ролей;
- блокування облікових записів при звільненні чи переведенні;
- хто адмініструє ролі.

## 5. Принципи обміну даними

1. **Назовні — лише агрегати після приховування і лише закритих циклів.** Ніколи не передаються окремі анкети, відповіді, коди доступу чи поєднання «категорія + підрозділ» окремого респондента.
2. **Однаковий поріг k для кожного зрізу.** Новий зріз проходить через ту саму функцію приховування (`backend/app/anonymity.py`). Система-отримувач зобов'язується не поєднувати зрізи, щоб обчислити приховані групи. Це умова угоди про обмін.
3. **Усередину — лише агреговані факти, а не списки людей.** Наприклад, система навчання передає «78% персоналу пройшли навчання», а не перелік прізвищ. Відсоток рахує система-джерело.
4. **Опис кожного факту:** ідентифікатор метрики, період, одиниця, охоплення, система-джерело, посилання на підтвердний документ. Роль, яка внесла факт, і роль, яка його підтвердила, різні. Зараз факти мають лише назву, значення й ознаку підтвердження ([methodology.md](methodology.md), розділ 9).
5. **Два контури не змішуються.** Анонімний `integrity.db` і персональний `v2_auth.db` не обмінюються даними. Персональні тестування не впливають на індекс і не передаються іншим системам ([V2_INTEGRATION_CONTRACT.md](V2_INTEGRATION_CONTRACT.md), розділ 1).
6. **Версія методики та хеші супроводжують кожен переданий індекс.**
7. **Жодного прямого доступу до БД.** Обмін іде лише через API або погоджені файли експорту. Отримувач читає дані сам; запис у модуль — лише через маршрути імпорту з перевіркою.
8. **Кожен обмін журналюється.** Зараз журнал дій фіксує видачу кодів, створення, активацію й закриття циклу, вхід після 2FA і створення адміністратора (`ALLOWED_ACTIONS` у `backend/app/audit.py`). Події експорту й імпорту потрібно додати до цього переліку.

## 6. Класи систем-джерел для об'єктивних показників

Кожному об'єктивному показнику seed (`backend/app/seed.py`, `OBJECTIVE_NAMES`) можна зіставити клас відомчої системи, що міг би передавати його як агрегат. Загальні точки інтеграції та їхній стан наведено в [integration-map.md](integration-map.md), розділ 7.

| Компонент | Показник | Клас системи-джерела | Що передається |
| --- | --- | --- | --- |
| C1 | Виконання заходів, закріплених за керівництвом, % | Система електронного документообігу (контроль виконання доручень) | % заходів, виконаних у строк за період |
| C2 | Актуальність антикорупційної програми, % | Система електронного документообігу (реєстр організаційно-розпорядчих документів) | % актуальних положень (визначення погодити) |
| C3 | Ризики з реєстру, щодо яких виконано заходи, % | Система управління корупційними ризиками | % ризиків із виконаними заходами |
| C4 | Скарги на оцінювання, розглянуті вчасно, % | Система управління освітнім процесом або облік звернень | % скарг, розглянутих у строк |
| C5 | Персонал, що пройшов навчання, % | Система управління навчанням; знаменник — кадрова система | % персоналу, що пройшов навчання |
| C6 | Повідомлення, на які відреаговано у строк, % | Система обробки повідомлень про порушення | Лише % повідомлень із реакцією у строк; зміст повідомлень і дані викривачів **не передаються** |
| C7 | Виконання плану заходів, % | Система планування антикорупційних заходів | % виконаних заходів плану |
| — | Довідник підрозділів, планова кількість учасників за категоріями | Кадрова система | Лише назви підрозділів і числа. Дає знаменник для `coverage.response_rate`, який зараз дорівнює `null` |

## 7. Дорожня карта

| Етап | Зміст | Умова переходу далі |
| --- | --- | --- |
| **0. Зараз** (хакатон) | Окремий модуль; Docker Compose локально; синтетичні дані; обмін через JSON API і PDF/XLSX; локальні облікові записи з 2FA | Демонстрація і рецензія журі |
| **1. Пілот** в одному закладі, закритий контур | Release-конфігурація (розділ 1), внутрішні реєстр образів і SMTP; затверджені методика й поріг k; обмін звітами з системою електронного документообігу вручну (PDF/XLSX) | Виконано перелік «Що обов'язково до роботи з реальними даними» з [abuse-analysis.md](abuse-analysis.md); пройдено негативні тести безпеки S1–S12 з V2-контракту |
| **2. Факти й довідники** | API введення об'єктивних показників з ідентифікатором метрики, періодом, одиницею, посиланням на доказ і підтвердженням другою роллю; імпорт довідника підрозділів і планової чисельності з кадрової системи (лише числа); сервісні облікові записи лише для читання; журналювання експорту | Затверджено опис метрик із власниками систем-джерел; тести на відсутність персональних даних в імпорті |
| **3. SSO і масштаб** | Вхід через відомчу систему ідентифікації (розділ 4); роль `auditor`; PostgreSQL ([integration-map.md](integration-map.md), розділ 7); кілька закладів із виміром «організація» і порогом k для кожного зрізу | Перевірено, що анонімна анкета працює без SSO; порівняння між закладами лише за однієї версії методики |
| **4. Екосистема** | Двобічний обмін Tracker ↔ система електронного документообігу (доручення, строки, посилання на докази); реєстр затверджених версій методики; офіційні анкети додатків Б і В після затвердження | Рішення замовника про статус методики |

**На жодному етапі не передбачено:**

- хмарних сервісів;
- передавання сирих відповідей;
- входу через SSO до анонімної анкети;
- автоматичних управлінських рішень: рекомендації лишаються пропозиціями, які приймає людина.
